# Diseño — ISO 27001 Fase 2: Gestión de Accesos

> **Fecha:** 2026-05-07
> **Sistema:** SOS Corp Checkup
> **Alcance:** Fase 2 — Puntos 4 (MFA) y 5 (Mínimo privilegio) · ISO 27001 A.9
> **Branch:** `feat/seguridad`

---

## Decisiones de diseño

- MFA **obligatorio** para rol `admin` (Opción A: forzado en próximo login sin MFA).
- MFA **voluntario** para rol `responsable` (accesible desde `/dashboard/responsable/ajustes`).
- Implementación vía **auth helper** en `lib/auth.ts` — extiende patrón existente `requireAdmin()`.
- Sin middleware (`proxy.ts` → `middleware.ts` queda para Fase 3 / OWASP).
- Sin packages externos — Supabase devuelve QR como SVG data URI, compatible con cualquier app TOTP estándar (Google Authenticator, Authy, Microsoft Authenticator).
- `requireAdmin()` se agrega como primera línea en **todas** las funciones de las 5 server actions admin.

## Punto 4 — Autenticación Multifactor (MFA)

### Lógica: `requireAdminWithMFA()` en `lib/auth.ts`

```
1. getProfile() → null → redirect /login
2. rol !== 'admin' → redirect /dashboard/responsable
3. supabase.auth.mfa.getAuthenticatorAssuranceLevel()
   - currentLevel='aal1', nextLevel='aal1' → sin MFA enrollado → redirect /dashboard/admin/mfa-setup
   - currentLevel='aal1', nextLevel='aal2' → MFA enrollado, sesión no verificada → redirect /dashboard/admin/mfa-verify
   - currentLevel='aal2' → ✅ pasa, return profile
```

`app/dashboard/admin/layout.tsx` reemplaza `requireAdmin()` con `requireAdminWithMFA()`.

### Página `/dashboard/admin/mfa-setup`

Client Component. Flujo:
1. `supabase.auth.mfa.enroll({ factorType: 'totp' })` → obtiene `totp.qr_code` (SVG data URI) + `totp.secret`
2. Muestra QR + clave manual (fallback)
3. Input de 6 dígitos para verificar
4. `supabase.auth.mfa.challengeAndVerify({ factorId, code })` → éxito → redirect `/dashboard/admin/empresas`

### Página `/dashboard/admin/mfa-verify`

Client Component. Para admins con MFA enrollado pero sesión en AAL1. Flujo:
1. `supabase.auth.mfa.listFactors()` → obtiene `factorId` del factor TOTP activo
2. Input de 6 dígitos
3. `supabase.auth.mfa.challengeAndVerify({ factorId, code })` → éxito (sesión sube a AAL2) → redirect `/dashboard/admin/empresas`
4. Mensaje de ayuda: si pierde acceso a app TOTP → contactar admin SOS Medical

### Sección Seguridad en `/dashboard/admin/ajustes`

- Muestra estado MFA: ✅ Activo / ⚠️ No activo
- Si activo: botón "Desactivar MFA" (con confirmación) → `supabase.auth.mfa.unenroll({ factorId })`
- Si inactivo: botón "Activar MFA" → redirect a `/dashboard/admin/mfa-setup`

### MFA voluntario en `/dashboard/responsable/ajustes`

Misma sección Seguridad pero sin redirect forzado. El responsable puede enrollar/desenrollar libremente. Si tiene MFA activo, el flujo de login lo lleva a verificar (Supabase lo maneja automáticamente en AAL).

## Punto 5 — Mínimo Privilegio

### `requireAdmin()` en server actions

Agregar `await requireAdmin()` como primera línea en cada función de:

| Archivo | Funciones |
|---------|-----------|
| `app/actions/empresas.ts` | `createEmpresa`, `updateEmpresa`, `deleteEmpresa` |
| `app/actions/sucursales.ts` | `createSucursal`, `updateSucursal`, `deleteSucursal` |
| `app/actions/chequeos.ts` | `createChequeo`, `updateChequeo`, `deleteChequeo` |
| `app/actions/usuarios.ts` | `createUsuario`, `updateUsuario`, `deleteUsuario`, `updateAsignaciones`, `reenviarCredenciales` |
| `app/actions/chequeos-pre-empleo.ts` | todas las funciones exportadas |

`requireAdmin()` ya existe en `lib/auth.ts`. En server actions, el `redirect()` interno lanza una excepción que aborta la función correctamente.

### Documentación de matriz de permisos

`docs/iso27001/fase-2-punto-5-minimo-privilegio.md` incluye:
- Matriz de permisos por rol (admin / responsable) con estado real de RLS
- Tabla de protecciones por capa (RLS + layout guard + action guard)
- Referencia a políticas RLS reales auditadas en Fase 0

## Criterios de éxito

- [ ] Admin sin MFA → redirigido a `/mfa-setup` al intentar acceder al dashboard
- [ ] Admin con MFA enrollado pero sesión AAL1 → redirigido a `/mfa-verify`
- [ ] Admin con sesión AAL2 → acceso normal
- [ ] Responsable puede enrollar/desenrollar MFA voluntariamente desde ajustes
- [ ] Todas las server actions admin rechazan ejecución si el usuario no es admin
